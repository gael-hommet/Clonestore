# Hydration mismatch (ISSUE-04) — root cause investigation

## Starting evidence (from the original 2026-07-23 audit, `CLONESTORE_ISSUE_REGISTER.md` ISSUE-04)
> Reproduction: navigation to `/demo`, full console capture — React reports a server/client mismatch on `style={{caret-color:"transparent"}}` for **all** `<input type="range">` and `<input type="number">` in the cost calculator. "This won't be patched up." Reproduced in a real browser, desktop 1440.

## Investigation performed in this block (2026-07-24)
1. Enumerated every `type="range"`/`type="number"` input in the entire `src/components/demo/` tree: exactly **2 files** contain one — `src/components/demo/cost/CapacityCalculator.tsx` (both a number and a range input per field) and `src/components/demo/acts/ValueChapter.tsx` (one range input in its "edit assumptions" disclosure).
2. Read both in full: both are fully **controlled** (`value={value}`, never `defaultValue`), initial state seeded from a constant (`ILLUSTRATIVE_INPUTS`) or derived deterministically — no `window`/`Date`/`Math.random`/storage read affects their initial value.
3. Grepped the entire repo (`src/`, all `.css` files, `globals.css`, `demo.css`, `pierre-demo.css`) for `caret-color`/`caretColor`: **zero occurrences anywhere.** No component, no stylesheet, no global reset sets this property on any element, let alone conditionally between server and client.
4. Read `src/lib/demo/presentation/cost-model.ts` (the pure calculation/formatting engine both sliders depend on): its own header comment explicitly documents avoiding `Intl.NumberFormat`/`toLocaleString` specifically **because** their separators depend on ICU version and would cause a hydration mismatch — hand-rolled deterministic formatting is used instead. This is a codebase that has already, deliberately, engineered around this exact class of bug once.
5. Read `src/components/demo/primitives/pinned.tsx` and `motion.tsx`: both carry explicit "SSR-safe, avoids hydration mismatch" doc comments describing why `prefers-reduced-motion` is never read during render.
6. Read `src/components/demo/cost/useSequentialReveal.ts`: explicit doc comment states initial state is deliberately "tout révélé" (fully revealed) specifically so SSR and first client render are identical, with accumulation starting only in a post-mount effect.
7. Checked `DemoExperience.tsx`, `ScenarioComparator.tsx`, and every other component touching these two sliders: all `window`/`matchMedia`/`Date`/`Math.random`/storage reads are confirmed inside `useEffect`/event handlers, never in the render path.

## Conclusion
**No source of the reported `caret-color:"transparent"` mismatch exists anywhere in this application's current code, CSS, or dependencies.** Combined with the original report's own description — the mismatch affected **every** range/number input **uniformly**, independent of which field or value — this is the well-documented fingerprint of a **third-party browser extension** (password manager, dark-mode, or accessibility tool) injecting a blanket style onto all text-editable form fields **before** React hydrates. This is an acknowledged, common false-positive class of React's hydration warning, explicitly caused by external DOM mutation the framework has no control over, not by application code.

## Honesty about what could NOT be re-verified live
Playwright was unavailable for this entire block (confirmed at block start). A fresh, live, extension-disabled-vs-extension-enabled browser capture to 100%-conclusively re-prove the extension hypothesis was **not possible this session**. The conclusion above is high-confidence, evidence-based (exhaustive negative search + the "affects all inputs uniformly" signature + surrounding deliberate SSR-safety engineering), but is not itself a fresh browser capture — this is stated plainly in `DEMO_HYDRATION_ROOT_CAUSE_REPORT.md` and the final verdict, rather than overclaiming a live re-reproduction that didn't happen.

## Fix applied
`suppressHydrationWarning` added to exactly the 3 affected input elements (2 in `CapacityCalculator.tsx`, 1 in `ValueChapter.tsx`), each with an inline comment explaining the justification — satisfying the master prompt's explicit condition for using this escape hatch ("le contenu est intrinsèquement non déterministe et qu'une justification écrite démontre que c'est la bonne solution"): the non-determinism here is externally injected by the user's own browser environment, not by this app's rendering logic, which remains fully deterministic (proven by the new SSR-determinism test, see file 07).
